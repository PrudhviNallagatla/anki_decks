What are Extension Modules?
 Additional Supplied Modules found in the “extension” directory provides
additional functionalities
 Extensions are not included in the core database and may be still under
development
 Extensions are also tied to that particular version of Postgres
 They are part of contrib package and can be installed using
 “dnf install edb-asXX-server-contrib”
 Package installer places extensions in directory:
/usr/edb/asXX/share/extension/

Partitioning
 Partitioning refers to splitting what is logically one large table into smaller
physical pieces
 Query performance can be improved dramatically for certain kinds of queries
 Improved UPDATE performance. When an index no longer fits easily in
memory, both read and write operations on the index take progressively
more disk accesses
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Partitioning Benefits
 Partitioning is useful for large tables especially when a table is bigger than physical
memory
 Can be used when different storage devices must be used for single table
 Seldom-used data can be migrated to cheaper and slower storage media
 Bulk loads or deletes may be accomplished by simply adding or removing one of the
partitions
 Partitioning avoids VACUUM overhead caused by a bulk DELETE
 Dramatic performance improvements for certain kinds of queries
 Improved UPDATE performance
 Index operations takes less time
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

When to Partition - Suggestions
 Here are some suggestions for when to partition:
 When a large table begins having performance issues
 Size of the table has exceeded the physical memory
 Tables greater than 20GB may be considered for table partitioning
 Tables containing historical data where the newest data can be added to a new partition
 A typical example is where 1 month of data is frequently updated and 11 months of data is read only
 When the content of a table needs to be distributed on different storage devices depending on
the usage of data
 When queries only need to access a subset of data

Attach and Detach Partitions
 A table can be added or attached as a partition to a partitioned table that exists
 An existing partition can be converted into a standalone table
 Example:
 ALTER TABLE users ATTACH PARTITION users_3 from (101) to (150);
 ALTER TABLE users DETACH PARTITION users_3;
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Partition Pruning
 Query planner uses partition pruning to compute an efficient plan
 Query filter must use a partitioned column
 In a LIST partitioned table partition pruning is effective when the WHERE clause has
equal(=) or AND operator
 In a RANGE partitioned table partition pruning is effective when the WHERE clause has
=,< or > operators
 In a HASH partitioned table partition pruning is effective when the WHERE clause has
equal(=) operator
 Partition pruning on Boolean columns
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Fast Pruning
 Fast pruning occurs early in the planning process
 Only works on queries with WHERE or JOIN clauses
 Controlled by a parameter named edb_enable_pruning
 Reduces the number of partitions that the planner must consider
 Doesn’t work on sub-partitioned tables or RANGE partitions partitioned on more
than one column
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Constraint Exclusion
 Constraint exclusion is like partition pruning except that it uses each table’s
check constraint
 Constraints defined for each partition are examined
 Controlled by the constraint_exclusion parameter which must be set to
either partition or on
 Constraint exclusion only works when the query's WHERE clause contains
constants or parameters
 It does not work if where clause is using any non-immutable function e.g
current_timestamp()
 All constraints on all children of the parent table are examined
 Exclusion constraints support to prevent conflicting data in different partitions
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Handling Stray Values
 Stray values are rows that do not meet any partitioning rules
 A DEFAULT or MAXVALUE partition or sub-partition can be used
to capture such rows
 The syntax of a DEFAULT rule is:
PARTITION [partition_name] VALUES (DEFAULT)
 The syntax of a MAXVALUE rule is:
PARTITION [partition_name] VALUES LESS THAN (MAXVALUE)

Connection Pooling
 Each database client acquires a database connection from the database
 The Postmaster is responsible for listening and providing database connections
 Connection processes are destroyed once the clients log off
 Connection pooling:
 Provides a mechanism to reuse the existing connection processes once the clients log off
 Lowers connection overhead on the postmaster
 Improves application database access performance
 Spreads connection cost over repeated clients
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

pgpool-II
 Open source
 Middleware between PostgreSQL servers and a
PostgreSQL database client
 pgpool-II talks to PostgreSQL backend and frontend
protocol, and relays a connection between them
 Features:
 Connection Pooling
 Replication
 Load Balancing
 Automatic Failover
 Parallel Query
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

pgpool-II Connection Pooling
 It saves connections to the PostgreSQL servers
 It will reuse connections whenever a new connection request with the same
properties (i.e. username, database, protocol version) is received
 It reduces connection overhead, and improves system's overall throughput
 Provides cluster-based connection pooling
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Load Balancing Reads
 If a database is replicated, executing a SELECT query on any server will return
the same result
 pgpool-II automatically detects SELECT and can load balance reads among
multiple servers, improving the system's overall throughput
 It works best in a situation where there are a lot of users executing many
queries at the same time

pgbouncer - "Bouncer is always right“
 Lightweight connection pooler for Enterprise Postgres
 Any application can connect to pgbouncer as it
connects with Enterprise Postgres
 It can help to reduce the connection impact on the
Enterprise Postgres
 It provides connection pooling(reuse) of the existing
connections
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

pgbouncer Features
 It has low memory requirements (2k per connection by default)
 It is a database-based pooler that can connect to a database from different
clusters
 Not tied to one backend server
 Supports online restart/upgrade without dropping client connections
 Supports Windows and Linux platforms
 Bundled in StackBuilder Plus for Windows and also available as package from
repos.enterprisedb.com
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Types of Connections
 pgbouncer supports several types of pooling when rotating connections:
 Session pooling
 A server connection is assigned to the client application for the life of the client connection
 This is the default
 Transaction pooling
 A server connection is assigned to the client application for the duration of a transaction
 Statement pooling
 A server connection is assigned to the client application for each statement

How Connections are Established
 An application connects to pgbouncer as if it were a Postgres database
 pgbouncer then creates a connection to the actual database server, or it reuses one of the
existing connections from the pool
 Step 1 - The client application attempts to connect to Postgres on the port where pgbouncer is running
 Step 2 - The database name supplied by the client application must match with the list in pgbouncer.ini
 Step 3 - The username and password supplied must match with the list in users.txt
 Step 4 - If a connection with the same settings is available in the pool it will be assigned to the client
otherwise a new connection object will be created
 Step 5 - Once the client logs off the connection object returns back to the pool

Setting Up pgbouncer
 Create a pgbouncer.ini file:
[databases] db1 = host=127.0.0.1 port=5444 dbname=db1
[pgbouncer] listen_port = 6432, listen_addr = 127.0.0.1, auth_type =
md5, auth_file = users.txt, logfile = pgbouncer.log, pidfile =
pgbouncer.pid, admin_users = someuser
 Create a users.txt file:
"someuser" "same_password_as_in_server"
 Launch pgbouncer:
$ pgbouncer -d pgbouncer.ini
 Have your application (or the psql client) connect to pgbouncer instead of
directly to the Postgres server:
$ psql -p 6432 -U someuser template1
