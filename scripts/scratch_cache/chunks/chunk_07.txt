Database Cloning
 Cloning creates a snapshot/copy of an existing database
 All the objects and data is copied over to a new database
 Cloning is different from replication or backup
 Enterprise Postgres provides rapid and space efficient cloning of a database
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Steps for Creating a Clone of a Database
 Identify the database to be cloned
 Identify a name for the new clone
 Verify no one is connected to the database to be cloned
 Run the CREATE DATABASE..TEMPLATE command to create a clone
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Cloning a Database Using pg_dump
 pg_dump can also clone a database between clusters
 All options of pg_dump can be used for customization and speed
 Need psql access to the database
 Create a new blank database before running pg_dump
 No need to remove connections from the to-be cloned database
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Clone Schema
 Enterprise Postgres includes Clone Schema extension that gives the ability to
make a copy of a schema with its database objects
 Schema can be copied into another database or into same database with
different name
 Cloning of a schema can be done in an online as well as in non-blocking,
background job mode
 Multiple background worker process can be used to shorten the time of
operation
© E DB 2 0 2 5 — A LL R I G HT S R E SE R V E D.

Example: Passphrase Protection
 Initialize the cluster using initdb with TDE:
initdb -D datadir1 -y --key-wrap-command='openssl enc -e -aes-128-
cbc -pass pass:edb123 -out "%p"' --key-unwrap-command='openssl enc
-d -aes-128-cbc -pass pass:edb123 -in "%p”’
 Data key is protected(wrap) using a passphrase
 Data key unwrap command is stored in postgresql.conf:
data_encryption_key_unwrap_command = 'openssl enc -d -aes-128-cbc -
pass pass:edb123 -in "%p“’
 Password can also be prompted during initdb and start-up using systemd-ask-password

Need to Upgrade
 Enterprise Postgres is an actively developed database
 Major releases include new features, capabilities and
performance enhancements
 Minor releases include security and data corruption
bug fixes
 EDB Postgres® AI recommends all users to run the
latest available minor release
 Not upgrading is riskier than upgrading
 EDB Postgres® AI aims to fully support a major
release for five years

Upgrading Best Practices
 Enterprise Postgres upgrade is not automatic
 Run pg_upgrade with --check option for any upgrade issues
 Take a full backup before and after upgrade
 If --link option is used with pg_upgrade, it’s unsafe to start old cluster
 Check for failed rebuild, and reindex cases reported by pg_upgrade
 Watch for post-upgrade warnings generated by pg_upgrade and run the generated
script on new database as Superuser
 Do not stop or abort the upgrade process once started
 In a streaming replication environment, replica server also needs upgrade
 Once verified, remove old cluster footprints
